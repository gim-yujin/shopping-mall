# 코드베이스 비판적 검토 — "재수행한다면" 관점

- 작성일: 2026-06-16
- 대상: shopping-mall 전체 (main 258개 / test 211개 Java 파일, 22테이블, 27개 마이그레이션)
- 평가 기준: Amazon / eBay / Coupang 수준의 상용 이커머스를 100점으로 가정
- 평가 태도: 아첨 없음. 약점 위주. 코드 근거 명시.

---

## 0. 결론부터

**상용 이커머스 기준 점수: 20 / 100.**

오해를 막기 위해 분리해서 말한다. 이 프로젝트를 "백엔드 동시성 포트폴리오"라는 다른 잣대로 보면 70점대다. 잘 만든 동시성 학습 프로젝트다. 하지만 질문이 "Amazon/eBay/Coupang을 100점으로 놓으면 몇 점이냐"이므로, **상용 쇼핑몰로서**의 점수를 매겨야 한다. 그 기준에서 이 프로젝트는 **장사를 할 수 없는 물건**이다. 이유는 단 한 줄로 요약된다.

> **결제가 없다. 주문은 생성되는 순간 무조건 `markPaid()` 된다.** (`OrderCreationService.java:300`)

돈을 받는 단계가 통째로 비어 있는 쇼핑몰은 정의상 쇼핑몰이 아니다. 나머지 정교한 동시성·관측성·테스트는 전부 "결제 0원짜리 가짜 주문"을 빠르고 안전하게 처리하기 위한 인프라다. 엔진은 F1급인데 차에 결제 모듈이라는 바퀴 하나가 없다.

## 2. 치명적 결함 (이게 점수를 끌어내린다)

### 2-1. 결제가 존재하지 않는다 — 가장 큰 거짓말
- `PaymentMethod`는 `CARD/BANK/KAKAO/NAVER/PAYCO` **enum 문자열일 뿐**이다 (`PaymentMethod.java`). PG 연동, 결제 승인, 결제 검증 웹훅, 환불 API 호출 그 무엇도 없다.
- 주문은 `buildAndSaveOrder()` 마지막에서 즉시 `order.markPaid()` 된다 (`OrderCreationService.java:300`). 즉 "결제대기(PENDING)" 상태는 코드상 거의 죽은 상태이고, 모든 주문이 생성 즉시 결제완료로 둔갑한다.
- 환불도 마찬가지다. `refundedAmount`를 숫자로만 증가시킬 뿐 실제 카드 취소·계좌 환불은 일어나지 않는다.
- **영향:** 정산, 매출, 미수금, PG 수수료, 부분환불 정합성 — 이커머스 회계의 절반이 통째로 시뮬레이션이다. 동시성으로 지킨 재고 정합성이 정교할수록, 그 위에 얹힌 "0원 결제"의 공허함이 더 두드러진다.

### 2-2. Redis-DB 이중 쓰기 정합성 구멍 (스스로 주석으로 자백함)
- `V4RedisStockDeduction` 자바독에 그대로 적혀 있다. "다건 차감의 atomicity는 best-effort 보상(Increment 롤백)에 의존", "Redis 장애 시 폴백 경로 필요(본 PR 외)".
- `RedisFlashSaleCommandService.purchase()`는 Redis `DECRBY` 성공 후 DB 주문을 만든다. 그런데 보상(`INCRBY`)은 **`DataIntegrityViolationException`만** catch한다 (`:92`). 그 외 예외(커넥션 끊김, 타임아웃, JVM 크래시)로 DB 트랜잭션이 롤백되면 **Redis 카운터는 깎인 채 남아 영구 미판매(undersell)** 가 발생한다. 반대 타이밍에선 oversell도 가능하다.
- 즉 프로젝트의 간판 기능인 "플래시 세일 동시성 안전"이 단일 노드 happy-path에서만 성립하고, 정작 장애 상황 — 플래시 세일에서 실제로 터지는 상황 — 에서 깨진다. ADR-0003에서 V4를 정량 측정까지 했지만 정합성 보강은 "본 PR 외"로 미뤄져 있다.

### 2-3. 프런트엔드가 데모 수준
- 상품 이미지가 없다. 체크아웃 화면조차 `<span>IMG</span>` 회색 박스다 (`order/checkout.html:46-48`).
- 이미지 "업로드"가 없다. `ProductImage`는 관리자가 **URL 문자열을 손으로 입력**하는 구조다 (`ProductService.saveProductImages`, `MultipartFile` 핸들러 0개). 저장소·리사이즈·CDN·썸네일 파이프라인 전무.
- `src/main/resources/static`에 **JS 파일이 0개**다. 장바구니 수량 변경, 위시리스트 토글 같은 상호작용도 풀 페이지 폼 제출에 의존하는 것으로 보인다. 모바일 앱·반응형 최적화·검색 자동완성 UX 없음.
- 추천(연관상품·개인화), 검색 랭킹/연관도, 광고, 셀러 마켓플레이스, 리뷰 이미지 — Amazon/Coupang을 Amazon/Coupang으로 만드는 요소가 전부 부재. 검색은 Postgres FTS 단건이다.

### 2-4. 알림은 로그 출력 스텁
- `OrderNotificationService`는 `log.info("[알림 스텁] ...")`가 전부다. 이메일·SMS·푸시 없음. 자바독이 "스텁"임을 인정한다. Outbox로 신뢰성 있게 전달하는 대상이 결국 `System.out`이다.

## 3. 구조적 문제 (작동은 하지만 비용이 크다)

### 3-1. 도메인 대비 명백한 과설계 (이력서 주도 개발)
한 명의 개발자가 만든, 결제도 없는 모놀리식에 다음이 다 들어 있다.
- 재고 차감 전략 **4종**(V1 비관/V2 낙관재시도/V3 CAS/V4 Redis) — 실제 운영은 하나면 된다. 나머지는 벤치마크 전시용이다.
- Outbox, 멱등성 레코드, 레이트리밋, 백프레셔, 서킷브레이커, CQRS read view, Java 21 구조적 동시성(preview), 가상 스레드.
- `docs/` 25개 + ADR + `load-test/` 348개 파일(4MB) + 루트의 분석 MD 산재.

이게 학습 목적이면 훌륭하다. 그러나 "상용 쇼핑몰"의 잣대로는 **핵심(결제)은 비었는데 비핵심(인프라 패턴 카탈로그)이 과포화**된 불균형이다. 시니어 리뷰어의 첫 질문은 "재고 전략이 왜 4개야? 운영에서 쓰는 건 뭐고 나머지는 왜 프로덕션 코드에 남아 있어?"가 된다.

### 3-2. 주석 고고학 (변경 이력이 소스에 화석화됨)
- `[Phase N]`, `[P0 FIX]`, `[P2-11]`, `[§13-2]` 류 **이력 마커가 main 소스에 374개**, 139개 파일에 분포한다.
- 예: `Order.java`의 필드마다 "기존 문제 → 수정" 서사가 붙어 있다. 이건 git 커밋 메시지·ADR에 있어야 할 내용이지 엔티티 필드 옆에 있을 내용이 아니다.
- 결과: 파일을 열면 "현재 코드가 무엇을 하는가"보다 "과거에 무슨 버그가 있었는가"가 먼저 읽힌다. 신규 합류자는 이미 해결된 과거를 재독해해야 한다. 역설적으로 프로젝트 CLAUDE.md의 "Surgical Changes / 현재 동작만 설명" 원칙과 정면충돌한다.

### 3-3. 스키마 마이그레이션 수동 적용
- `ddl-auto: validate`는 옳다. 그러나 Flyway/Liquibase가 **없다.** `migration/`은 손으로 만든 `V2~V27` SQL이고, V23/V24 주석에 "운영 배포는 본 마이그레이션 수동 적용 필수"라고 적혀 있다. 휴먼 에러·환경 드리프트의 직접적 원인이고, 상용에서는 사고 난다.

### 3-4. 플래시 세일 주문은 가짜 주문
- `Order.createForFlashSale()`는 배송지를 `"(플래시 세일 주문 — 배송 정보 미입력)"` 플레이스홀더로 채우고, 할인·적립·배송비 0, `markPaid()` 즉시 호출. 동시성 벤치마크용 더미 주문이지 사용자가 실제로 받는 물건이 아니다.

## 4. 공정하게 — 잘한 것 (점수를 떠받치는 부분)
아첨이 아니라 사실이다. 한 자릿수가 아닌 이유다.
- **테스트가 진짜다.** 211개 파일, 동시성 테스트 31개. `CartConcurrencyTest`는 Lost Update / 한도 우회 / UNIQUE 충돌을 `CountDownLatch`+`ExecutorService`로 실제 경합시켜 검증한다. 포트폴리오에서 보기 드문 수준.
- **Security 구성이 견고하다.** `/api/**`와 웹을 별도 `SecurityFilterChain`으로 분리, API는 CSRF off·JSON 401, 웹은 CSRF 쿠키·로그인 차단 필터·레이트리밋을 `AuthorizationFilter` 뒤에 정확히 배치. 필터 이중등록 방지(`FilterRegistrationBean.setEnabled(false)`)까지 챙김.
- **주문 생성 분해가 깔끔하다.** God class를 `CartSelectionResolver`/`StockProcessor`/`PostProcessor`로 쪼개고, `createOrder()`는 8단계 오케스트레이터로만 남겼다. 가독성 양호.
- **관측성 기본기**가 있다. Micrometer 타이머, HikariCP 튜닝(풀 17, lock_timeout 5s, leak detection), `open-in-view: false`, 가상 스레드까지 근거를 갖고 설정.
- **ADR 문화**가 있다. 락 전략 선택을 정량 측정과 함께 문서화한 점은 실무 감각을 보여준다.

## 5. 다시 한다면 — 우선순위順 (Top 8)

1. **결제부터 만든다.** Toss Payments/아임포트 샌드박스라도 붙여 PENDING→결제요청→웹훅 승인→PAID 상태기계를 실제로 돌린다. `markPaid()` 즉시 호출을 제거한다. 이것 하나가 8점→40점대로 끌어올린다.
2. **재고 전략을 1개로 줄인다.** 운영 경로는 V1(비관) 또는 V3(CAS) 하나만 프로덕션에 남기고, V2/V4와 벤치마크는 별도 모듈/브랜치/`benchmark` 소스셋으로 격리한다. 프로덕션 코드에 전시품을 두지 않는다.
3. **Redis-DB 정합성을 닫는다.** 플래시 세일을 한다면 Redis 예약 → Outbox/메시지로 DB 확정 → 실패 시 Redis 보상까지를 한 트랜잭션 경계+보상 스케줄러로 묶는다. catch를 `DataIntegrityViolationException`에서 모든 실패로 넓히고, 크래시 복구 테스트(awaitility)로 증명한다.
4. **Flyway 도입.** 수동 SQL 적용을 없앤다. 30분 작업이고 사고 한 건을 막는다.
5. **주석 고고학 제거.** `[Phase N]/[P0 FIX]` 이력 서사를 소스에서 걷어내 ADR/CHANGELOG로 이관한다. 주석은 "지금 무엇을/왜"만 남긴다. 374개 → 50개 목표.
6. **프런트 최소 현대화.** 실제 이미지 업로드(MultipartFile→오브젝트 스토리지) + 썸네일, 장바구니/위시리스트 비동기 토글(JS), 검색 자동완성. 또는 솔직하게 "REST API + 별도 SPA"로 포지셔닝하고 SSR 템플릿을 데모로 격하.
7. **알림 스텁 실체화.** 최소한 콘솔이 아닌 메일(MailHog/SES 샌드박스)로 Outbox 소비를 끝까지 연결해 "신뢰성 있는 전달"을 진짜로 증명한다.
8. **README의 수사 톤 정리.** "대규모 트래픽 설계"는 단일 노드·단일 DB·결제 없음이라는 실제 범위와 맞지 않는다. 범위를 정직하게 좁혀 적는 편이 신뢰를 준다.

## 6. 한 문장 총평
**"동시성 엔진은 잘 깎았으나, 그 엔진이 굴리는 것이 0원짜리 가짜 주문이라는 점에서 상용 이커머스로는 20점."** 결제·프런트·정합성 세 구멍을 메우면 같은 코드 자산으로 50점대까지 단기간에 갈 수 있다. 지금은 "쇼핑몰을 만든 프로젝트"가 아니라 "쇼핑몰을 소재로 동시성을 공부한 프로젝트"다 — 그리고 그 사실을 README가 인정하지 않는 것이 가장 정직하지 못한 부분이다.
