## 1) 실험 목적 / 조건

- 목적: *(캐시 OFF, 인덱스 ON)* 조건에서 **OSIV ON**이 성능/안정성에 주는 영향을 관찰
- 조건: **캐시 OFF / 인덱스 ON / OSIV ON**

## 2) Executive Summary (핵심 결론)

- **shopping**: 매우 안정적 (HTTP 실패 0%, Checks 100%, p95 ≈ 12~13ms)
- **browse**: p95가 수 초 단위(≈ 2.84s)이며 **HTTP 실패율 ≈ 1.84%**, Checks도 99% 기준 미달(≈ 98.16%)
- **coupon_rush**: HTTP 실패는 없으나 **쿠폰 발급 p95 ≈ 1.05s**로 목표(예: p95 < 1s)에 근접/초과 → tail 개선 필요
- **mixed**: 혼합 트래픽에서 **HTTP 실패율 ≈ 6.77%**, Checks ≈ 93.71%로 가장 불안정  
  (동시성/혼합 트래픽에서 자원 경합이 심해지는 패턴)

  → 이번 결과에서 TTFB가 지배적이고(mixed/browse), 실패율이 증가한 패턴은 “리소스 포화/대기” 가설과 정합성이 있습니다.

## 7) 추천 액션 아이템 (우선순위)

### P0. mixed/browse 실패 원인 규명(필수)
- 동일 시간대 앱 로그에서 **5xx/timeout/DB 예외(커넥션 획득 실패 포함)**를 집계
- HikariCP 등 커넥션 풀 지표: active/idle/wait time, acquire timeout 발생 여부 확인
- DB 슬로우쿼리(특히 home/products/search/category) 수집 및 실행 계획(EXPLAIN) 확인

### P0. browse 병목(홈/목록/검색) 우선 최적화
- `GET /`(home)에서 불필요한 조인/집계 제거, 응답 DTO 고정 + 필요한 연관만 fetch
- 상품 목록/검색 쿼리 인덱스/정렬/페이징 전략 점검(OFFSET 비용 포함)

### P1. coupon_rush tail 개선
- “성공 발급” vs “소진” 응답을 분리 계측(tag)하여 **성공 경로 p95**를 따로 관리
- 발급 API에서 락 경합(행락/분산락) 구간을 프로파일링

### P1. OSIV 영향 분리 재실험(권장)
- 동일 데이터/동일 warm-up/동일 배포에서 **OSIV ON vs OFF**만 토글하여 A/B 재측정
- 직렬화에서 Lazy Loading이 발생하는지(엔티티 직접 반환, Jackson 설정 등)도 함께 점검
