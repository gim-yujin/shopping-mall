# 쇼핑몰 k6 부하 테스트 결과 분석 보고서 (캐시 비활성화)

## 2) 테스트 구성 요약(스크립트 기반)

### 공통 특징

* **VU당 1회 로그인 후 세션(쿠키) 재사용** → 쿠폰/주문 성능 관찰 목적(로그인 반복으로 인한 노이즈 축소).
* 핵심 메트릭:
  * `http_req_duration`(요청 총 시간), `http_req_waiting`(TTFB), `http_req_failed`(요청 실패율) 등
  * 커스텀: `login_duration`, `coupon_duration`, `orders_created`, `coupons_issued` 등
* `http_req_duration`는 **sending + waiting + receiving**이며, DNS/커넥션 시간은 별도 지표로 분리됩니다.

 **browse:** 최대 100 VU, 약 9분(50→100 VU 램프업/홀드)

* **shopping:** 최대 50 VU, 약 9분(20→50 VU 램프업/홀드)
* **coupon_rush:** 최대 100 VU, 약 40초(10초 내 100 VU 스파이크)
* **mixed:** 최대 180 VU, 약 10.6분(탐색+쇼핑+쿠폰+소셜 혼합)

  * 혼합 트래픽 상황에서 리소스 경합이 잘 드러나는 구성

## 3) 전체 결과 요약(Executive Summary)

### 한 줄 결론

* **shopping 단독은 “매우 안정적/고성능” (3/3 PASS)**
* 하지만 **browse / mixed는 p95가 수 초 단위로 상승**하여 **성능 목표(특히 endpoint p95<1s)** 를 크게 미달

## 5) 공통 패턴 진단(가설) — “TTFB 지배 + 리소스 포화”

* k6에서 `http_req_waiting`은 **서버가 첫 바이트를 돌려주기까지의 시간(TTFB)** 성격입니다.
* browse/mixed/coupon_rush에서 공통적으로 **waiting(p95)이 수 초~1초대**로 커지고, blocked/connecting은 미미 →
  **(추정) 서버 내부 큐잉/락 경합/DB 병목/스레드풀 고갈** 중 하나 이상이 발생.

## 6) 개선 우선순위 제안(액션 플랜)

### P0. Browse 병목(홈/카테고리) 최우선 완화
1. 홈(/) 렌더링/쿼리 비용 제거
   * 홈에서 “베스트/신상/인기/추천” 같은 섹션을 DB에서 실시간 집계한다면 → **사전 집계/캐시**로 전환
   * 가능하면 **CDN + 캐시 헤더**(정적/준정적 영역) 적용
2. 카테고리/상품목록 쿼리 최적화
   * 정렬/필터에 필요한 **복합 인덱스** 점검
   * N+1, 불필요한 join 제거, 페이징 방식(OFFSET 비용) 개선(예: keyset pagination)
3. 검색(/search)
   * DB LIKE/풀스캔이면 즉시 병목화 가능 → 검색 인덱스/전용 검색엔진(Elastic 등) 고려

### P0. Mixed에서 “읽기 vs 쓰기” 격리(핵심 전환 경로 보호)
* DB 커넥션 풀을 read/write로 분리하거나(또는 읽기용 replica)
* browse 트래픽이 폭증해도 checkout/order_create가 커넥션을 못 얻어 밀리지 않게 설계
* 우선순위/레이트리밋/로드셰딩: 포화 시 browse를 더 빨리 제한하고 결제·주문은 보호

### P1. 쿠폰 러시(동시성) 처리 개선
* 원자적 차감(remaining > 0) + 중복 발급 방지(예: Redis/Lua)
* 성공 응답과 소진 응답을 태그로 분리해서 p95를 별도 측정

### P1. 로그인 스파이크(이벤트 당일 현실 반영)
* 이벤트 트래픽에 로그인/세션갱신이 섞일 가능성이 있으면, 로그인 경로도 방어 필요

### P2. 테스트 설계 개선(“용량”을 더 정확히 재기)
* `ramping-vus` 대신 arrival-rate 계열 executor 사용 권장
* 성공/실패(소진)/중복 등 비즈니스 결과별 latency 분리
* 서버측 APM/트레이싱 + DB 슬로우쿼리 샘플링
